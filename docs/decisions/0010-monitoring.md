# 0010. Monitoring: one Grafana over two Prometheus servers

- Status: accepted
- Date: 2026-10-17

## Context
The legacy cluster had a monitoring stack that was dropped when it was wiped (ADR 0009). Two machines now run clusters from this repo: the Lenovo (`extreme`, 30 GiB of RAM, the primary) and the Mac mini (`zion`, to be renamed `mini`; an 8 GiB host with a 5 GiB Lima VM, today serving production Immich). I want one dashboard that shows both, alerts on my phone, and the problems this homelab has actually had visible: a full disk, a 100 Mb/s network link, a GPU that silently stopped working after a driver upgrade, Flux not syncing, and a nightly backup that did not run.

## Decision
- **The stack is `kube-prometheus-stack`** (Prometheus Operator, Prometheus, Alertmanager, Grafana, node-exporter, kube-state-metrics), installed by Flux as a HelmRelease with the chart version pinned. It is the standard tool, so I learn the real thing (ServiceMonitors, alert rules), and both clusters use the same one.
- **One Prometheus per cluster, one Grafana.** Each cluster keeps its own metrics, so a broken link or a dead machine does not lose the other's history. Grafana runs on the Lenovo and has two data sources, `extreme` and `mini`, so a single overview dashboard can show both. No federation or `remote_write`.
- **The mini gets a trimmed install** (no Grafana, no Alertmanager, a small Prometheus, 7 days of retention) and only after the Immich cutover: today its VM carries production, and the stack costs roughly 600 to 800 MB. Its Prometheus is reached from the Lenovo over the tailnet: a NodePort, a Lima port forward, and `tailscale serve` on the Mac, the same pattern as the Cloudflare route. The macOS host is covered by `node_exporter` installed with Homebrew, scraped through `host.lima.internal`.
- **Access is tailnet-only** (a Tailscale sidecar, named `<app>-<machine>`), with no public hostname. Admin credentials are SOPS secrets.
- **Grafana is stateless:** dashboards, data sources and alert rules are in Git and loaded from ConfigMaps.
- **Prometheus data is disposable** (15 days on the Lenovo, 7 on the mini) and is not backed up. This is a deliberate exception to "every stateful app has a backup".
- **Alerts go to Telegram** through Alertmanager, with the bot token in a SOPS secret. A dead-man's switch covers the case where the Lenovo itself is down: the always-firing `Watchdog` alert sends a heartbeat to an external service, which notifies me when the heartbeats stop.
- **What is watched:** disk usage on `/` (alert at 80%), the network link speed, the GPU and the device-plugin DaemonSet, Flux Kustomizations and HelmReleases, pod crash loops and memory pressure, Immich (its built-in Prometheus metrics), the Cloudflare tunnels, and the nightly backup jobs (the scripts write a "last success" timestamp to node_exporter's textfile directory; an alert fires when it is older than about 26 hours).
- **Rollout in stages:** (1) the stack on the Lenovo with nothing sensitive: Prometheus, Grafana, Alertmanager, exporters, checked through a port-forward; (2) SOPS secrets, tailnet access, Telegram, the k3s and GPU rules; (3) Immich and backup-job metrics and the dashboards in Git; (4) the mini after the cutover, the overview dashboard, the dead-man's switch. Logs (Loki) and file browsing come later.

## Later: talking to Telegram
A bot that answers commands is a good idea if it stays read-only: `/status`, `/disk`, `/pods`, `/flux`, backed by a small service with a read-only ServiceAccount, answering only my chat ID. It must not change the cluster: changes go through Git (CLAUDE.md, "everything in Git"). If I ever want actions, the bot proposes a pull request instead of applying anything.

## Alternatives considered
- **Grafana Cloud or another hosted service:** easy, but the data leaves hardware I own.
- **VictoriaMetrics:** lighter, but less standard, and I want the Prometheus Operator model.
- **Thanos, Mimir or `remote_write` into one store:** more moving parts than two machines need, and the mini's VM cannot reach the tailnet by itself.
- **Grafana on the mini:** it is the standby with an 8 GiB host and cannot restart unattended while FileVault is on.
- **Netdata, Beszel, Uptime Kuma alone:** simpler, but not the Grafana and Prometheus tooling I want to learn. Uptime Kuma may still serve as the external heartbeat receiver.

## Consequences
- The chart is large and moves quickly (a new release most days), so the version is pinned and upgrades are deliberate commits. Helm silently ignores unknown values keys, so every key in the values was checked against the pinned chart.
- The first Grafana admin password is generated by the chart into a Secret. Stage 2 replaces it with a SOPS secret.
- A separate Flux Kustomization (`monitoring`) applies this, so a failing monitoring release cannot block the apps.
- Metrics are lost if the Lenovo's disk is lost; accepted.

## Update 2026-10-21
The mini's cluster is called `mini` (renamed from `zion` on 2026-10-20), and its Immich is no longer production: Immich cut over to the Lenovo on 2026-10-20 to 21. So the condition for stage 4 (the mini's trimmed install, "only after the Immich cutover") is met, though the mini still runs old copies of Immich and Actual in its 5 GiB VM and the memory cost still applies. The Lenovo's nightly NAS backup job (`hosts/ubuntu-extreme/backup/`) does not yet write the "last success" timestamp to node_exporter's textfile directory that the backup alert needs, so that alert cannot fire yet. The Postgres of Immich on the Lenovo now has 2 CPU and 3Gi of limits, which the Immich metrics should be checked against.
